## 2. Task 1: reproduction of the minimized seed-678 counterexample

Data (`_audit/m5/min1.tab`, weights in last field):

a d 2

`min2.tab` = the same plus `d 1` (needed without `-x`). Original seed 678 data in `_audit/m5/s678.tab`.

`{b,c}` is wrong in C: transaction `d b a c` is the only one with `b`, so supp({a,b,c,d}) = 1 = supp({b,c}).
With the 16-items machine C happens to be right, because upstream's machine ignores `xmax`
(consistent with doc §3.6).

**Root cause verified.** I re-derived the trace by hand from the data and the code order (`-q-1`: b=0, c=1, a=2, d=3; descending processing; post-order reporting; xmax = zmax+1 = 3 in `isr_setupx`, `report.c:1117`):
`{d,a,c}:2` is reported without its subtree being explored ({d,a,c,b}, size 4 > xmax), then
`{d,c}` (supp 2) is add-rejected by stored `{d,a,c}:2`, `{a}` (supp 4) by `{d,a}:4`; so none of the witnesses
`{d,c,b}`, `{a,c,b}`, `{d,a,c,b}` is ever stored and `{c,b}:1` passes `cm_supp = -1`. All rejections are by
genuine sets with true supports. The first violated invariant is indeed I1 (subtree completeness) at the report of
`{d,a,c}`, and I2 (a superset witness is stored when a set is decided) fails first at `{c,b}`. Agreed with the doc.

## 3. Task 2: review of the mathematical argument

### 3.1 Definitions used (consistency check)

| source | closed | maximal |
| --- | --- | --- |
| upstream `fpgrowth.html` | no superset with the same support | "no superset is frequent", ∀ J ⊃ I: supp(J) < smin (no size qualification) |
| `internal/oracle` (`isClosed`, `isMaximal`; doc.go: "decided against all supersets regardless of zmax") | all supersets | all supersets |
| `extcheck.go` / doc §3.1 | one-item extensions over all items | one-item extensions over all items |
| my brute force | all proper supersets (O(4^k) loop for k ≤ 10; exact superset-max DP for k > 10) | same |
| upstream code intent (`xmax = zmax+1`) | find a witness one level up | same |

So "maximal with `-n`" means **maximal in the whole lattice (no frequent superset of any size), then filtered by
size**. It is *not* "no frequent superset of size ≤ zmax". The code, docs, oracle, my brute force and upstream's
documented definition agree. Upstream's empty-output behavior for `-tm -n2` on `d2000x40d60` (0 sets) agrees too.
Edge semantics also agree with C: the empty set is never maximal, closed empty set at `-m0` iff no item has full
support, "no (frequent) items found" aborts with no output, `-n0` gives only the closed empty set.

### 3.2 Proof review (doc §3), step by step

- **One-item sufficiency (§3.1): proven.** If Y ⊋ X with supp(Y) = supp(X), any j ∈ Y\X gives
  supp(X) ≥ supp(X∪j) ≥ supp(Y) = supp(X). Same for frequency. This needs only non-negative weights
  (anti-monotonicity), which holds: `tract` rejects negative weights (`ErrNegativeWeight`, bag.go:106).
  Gap (M5A-4): the universe E is the recoded items; items removed by recoding are infrequent, so
  supp(X∪j) ≤ freq(j) < smin ≤ supp(X) — not stated, but true. Items removed by `-R` selection are outside the
  universe by upstream semantics (oracle agrees).
- **Zero weights and covers (§3.2): proven.** With w ≥ 0, supp(X∪j) = supp(X) iff j is in every positive-weight
  cover transaction. A perfect extension p of prefix N has supp(N∪p) = supp(N), so cover⁺(N) ⊆ cover(p), hence
  cover⁺(N) = cover⁺(N̂). Inherited pex of an ancestor P: cover⁺(N) ⊆ cover⁺(P) ⊆ cover(p). So
  `checkPath(rep.Items(), set, supp)` using the prefix's cover is correct. Checker and miner use the same bag
  object (`mine.go:82–96`), so the zmin-filtered, recoded, selected database is consistent between them.
- **zmin filter: proven.** The bag empties transactions with < zmin items. The check runs only after the
  `r.cnt+n < r.zmin` gate (report.go:585), so |N̂| ≥ zmin; supports of N̂ and of all its supersets are unchanged
  by the filter, so closedness/maximality is the same as in the unfiltered data. Repository decisions on small
  sets are made in the filtered bag consistently, which is all §3.4 needs.
- **Order facts (§3.3).** Verified in code: closed/maximal set `dir = -1` (`topLevel`), `-Ad → -As`, reorder
  (`-j` off) cleared (`config.go:269–276`). The 16-items machine's `count` pushes reduced patterns down before
  an item is processed, so `clear(i)` instead of `project(i)` under `!deeper()` (`fim16.go:397`) does not lose
  support of lower items (checked `m16.count`/`project`). Post-order: every `rec*` reports after the recursion.
- **Divergence lemma: proven** for the variants as described (shared prefix Q, m processed before c ⇒ m > c;
  m in Q's conditional tree ⇒ not a pex of Q or an ancestor; everything in N's subtree is < c). Top-level pex are
  in every set and never in a tree, so they don't break it.
- **Repository soundness (§3.4): proven.** I checked the actual criteria in `clomax.go`: `add` rejects iff a
  stored superset of prefix∪{item} has support ≥ supp (both targets; this is the closed criterion, also for
  maximal — so the maximal add-rejection argument via cover(S) = cover(X) ⊇ cover(Y) is valid); `Report` rejects
  iff `rs ≥ s || rs ≥ sto` (sto = 0 for maximal); stored sets are always frequent (miner adds only frequent items)
  and genuine (true supports; pex have full support). Head-union-tail: S ⊇ prefix ∪ tail, S ∪ pex(N) is frequent
  and contains the divergence item ⇒ no maximal set in the subtree. Storing sets the check later rejects
  (`update` before the check) keeps the repository genuine, so it is harmless — sound.
- **Reachability (§3.5): proven.** `deeper()` = |N| + |inherited pex| < zmax evaluated after `Add`, before the
  local pex are added; `xable2()` = Len + PexCount + 2 ≤ zmax at the parent, which is the same condition for any
  child. Canonical path argument holds (next item = max(C \ P̂) is frequent with P, not a pex of P, below P's last
  item, not eliminated by an ancestor). Chain shortcut adds only true pex (single node ⇒ all ancestors full support).
- **Uniqueness: proven** (divergence item or child's extra item distinguishes N̂'s). My harness compares
  multisets (duplicate lines would be flagged): none seen.
- **Unlimited case: proven safe.** When zmax ≥ `bag.MaxSize()` no checker is installed and `xable2()` returns
  true for closed/maximal (no `Xable` limit) and the machine is unlimited, i.e., full search, where no set is
  filtered by size. `MaxSize` is computed at insertion and never decreased by `Pack`/reduction (bag.go:176, 292),
  i.e., conservative: an over-estimate only switches on the (exact) limited path.

**Conclusion:** the theorem (reported = exactly closed/maximal sets in [zmin, zmax] passing the support/border/
evaluation filters) follows from the stated lemmas, *given* that the miners compute correct supports and correct
perfect extensions, and that traversal order matches §3.3. Those two premises are properties of the
implementation, supported by testing (golden C comparisons, oracle tests, my runs), not by proof.

### 3.3 Proven vs. tested

Proven (pen-and-paper, reviewed above): one-item sufficiency; zero-weight cover equality; zmin-filter invariance;
repository soundness (no false rejection, no lost closed/maximal subtree, HUT safe); reachability of every
closed/maximal set with |C| ≤ zmax under `deeper`/`xable2`; uniqueness; exactness of the unlimited path; that the
complete check's verdict depends only on N̂ and the database; that `clear` vs `project` in the machine is
support-neutral.

Supported only by testing: that each miner variant's actual traversal satisfies §3.3 (descending, lower-codes-only
projections, post-order, packed-head ordering for `-As -l`, `-Ac` machine mapping, `-At` root order); that
conditional supports and perfect extensions are computed correctly; that the bit-set code (`and`, `seek`,
`covers`, `suppWith`, weight planes, path cache invalidation, stamps) computes what §3.2 assumes; the cost model
in `decide` (affects speed only).

## 4. Task 3: implementation checks (all items, representations)

- **All eligible items are checked, including those absent from the conditional tree:** yes. The checker is built
  from the bag (`bag.All()`), `k = bag.NumItems()`; `vertClosed`/`vertMaximal` iterate `c.order` = all k items
  (descending frequency, early exit only at the first item with freq < supp resp. < smin — sound because the order
  is by frequency over positive-weight transactions); `scanClosed` starts from all items of the first cover
  transaction; `scanMaximal` counts every item in every cover transaction. No dependency on the search position.
  The mutation that hides items above the set (`mutB`) is caught by my harness (888 of 3,300 runs dense,
  38 of 50 sparse).
- **Packed entries** (`-As -l…`): unpacked to codes 0..30 in `newExtChecker` (bit b ↔ code b); reporter never
  `Add`s a packed head (otherwise `load` would index out of range; never observed).
- **Horizontal vs vertical:** `decide` chooses by estimate only; both paths are exact (also verified by the repo's
  `TestExtCheckBrute`, which forces scan and vertical). Intersection idempotence makes the 8 spread probes harmless.
- **Bitset ops:** dense rows, sparse merge (within 4x), gallop (`seek`) both directions; covers of every form.
  A mutation in the sparse merge path (`mutC`/`fpgD`) is caught by my sparse harness (20 failures in 75 runs).
- **Weights:** zero-weight transactions skipped consistently; `planes == nil` iff all positive weights are 1, so the
  popcount shortcut is only used for unit weights; `suppWith` sums `popcount << p` over ⌈log2(maxW+1)⌉ planes;
  maximal scan accumulates `txW`. Tested with weights 0..3, 0..999, up to 2^40 (40 planes), merged duplicates.
- **Overflow:** supports are int64 and bounded by the total weight (bag checks). Transaction indices are int32
  (`nz*64+bit`), which would overflow beyond 2^31 distinct transactions, but the bag trie itself uses int32 node
  indices, so that size is unreachable. Stamp wrap (`setStamp == 0`) handled. Not an issue.
- **Early exits:** closed scan stops when no candidate is left (= closed) — correct; maximal scan/vertical stop at the
  first frequent extension (= not maximal) — correct; vertical closed stops at the first item rarer than the set.
- **Path cache:** levels revalidated item by item against `rep.Items()`; covers depend only on the item set, so
  reuse is correct. `check` (empty prefix) uses separate scratch and leaves the path levels intact.
- **Where the check runs:** in `Report` after the repository and support/size gates, guarded by
  `r.cm != nil && r.cnt+n <= r.zmax` — before border, evaluation, count-only and sink. Rule-based evaluations
  (`-e` other than `b`) take the item-set-tree path (`mineTree`), not this code; I tested that path too (below).

## 7. Findings

### M5A-1 (Low, confirmed): maximal limited check dominates on dense data with many maximal zmax-sets

- Files/functions: `internal/fpg/extcheck.go` `decide`, `scanMaximal`, `vertMaximal`.
- Evidence: `d20000x200d30.tab -tm -s2 -n3`: Go 99.7 s vs C 39.0 s (2.6x), while `-tc` on the same data is
  12.1 s (C 46.2 s). Every reported maximal set must have *all* one-item extensions shown infrequent, so the check
  cannot exit early: Σ|t| over the cover (or k × cover words) per set, 1.3 M times. C pays the same information
  cost by exploring zmax+1, but on compressed FP-trees.
- Reproduction: `cd _audit/m5 && ./meas.sh x ./fpg -tm -s2 -n3 data/d20000x200d30.tab -` (data generation in §6).
- Impact: performance only; exact output (C is not exact in general, B5). Go still uses 11x less memory than C here.
  The doc's §8 statement of a "bounded overhead" is measured only on sparse data; dense maximal at -n3 is the worst
  observed ratio to C.
- Proposed fix (optional): share work among siblings at boundary nodes. For a parent prefix P whose children are
  not projected, one pass over cover(P) computing supp(P∪{j}) for all j gives an upper bound
  supp(P∪{h}∪{j}) ≤ supp(P∪{j}); only items j with supp(P∪{j}) ≥ smin need per-child testing (and pairwise
  supports supp({h,j}) give a second cheap bound for small k). Or document the case in `docs/m5-investigation.md` §7/§8.
- Blocks v0.1.0: no.

### M5A-2 (Info, confirmed): checker memory overhead

- Evidence: vs1M `-n1` 297.7 MB vs unlimited 248.1 MB (+50 MB, +20 %), C 146.5 MB; sparse-large +20–24 MB.
- Impact: linear and bounded (≤ ~36·O + 24·T bytes plus per-item arrays); acceptable. The doc's path-cache bound
  (12·W·zmax) is correct but loose; Σ ≤ 12·O holds.
- Fix: none needed; optionally state the tighter bound.
- Blocks: no.

### M5A-3 (Info, confirmed): minimized case also reproduces on upstream C

- Evidence: §2 table — C 6.21 reports `c b (1)` for min1/min2 (`-tc` and `-tm`) with `-As -l0`, `-Ac -l0`,
  `-Ad -l0`, `-At`, and `c b (4)` for the original seed 678 data with the same variants; correct with the
  16-items machine.
- Impact: the doc (§2.1–2.2) presents the minimized case as a failure of the recreated boundary-pex attempt; it is
  also a minimal, 4-transaction B5 reproducer for upstream, which is stronger evidence for deviation M5.
- Fix: add the C output to `docs/m5-investigation.md` §2.2 and/or `docs/upstream/fpgrowth-core.md` B5.
- Blocks: no.

### M5A-4 (Info, confirmed in doc): proof presentation gap

- Where: `docs/m5-investigation.md` §3.1–3.2.
- The universe E is "codes after recoding"; the doc does not state why items removed by recoding cannot violate
  closedness/maximality (supp(X∪j) ≤ freq(j) < smin ≤ supp(X)). It also relies, without saying so, on the
  reporter's stored sets always being frequent (true: miners add only frequent items) for the maximal report
  rejection. Both are one-line additions; the theorem is unaffected.
- Blocks: no.

### M5A-5 (Info, confirmed): sparse-row vertical branches are practically unreachable in production

- Files: `extcheck.go` `covers` (sparse branch), `suppWith` (sparse branch), `vertClosed`/`vertMaximal` on sparse
  items.
