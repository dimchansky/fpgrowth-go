### D-1 (Medium): merge-order dependency on PR #3

The README states, as current behavior:

- `TableFormat{FieldSeparators: ";"}` is rejected with `ErrInvalidOptions`;
- a nil `SourceFunc` is `ErrInvalidOptions`;
- a `MaxSupport` below a same-kind `MinSupport` is rejected;
- an invalid `Options.Items` item matches both `ErrInvalidOptions` and `ErrInvalidItem`;
- `SpoolTable`/`SpoolCSV` reject an invalid format before copying.

I checked all of this against `origin/fix/api-audit` with a throwaway
test, and it holds there. On `main` and on the PR head none of it exists.
If #4 is merged first, the README on `main` documents behavior that does
not exist.

Suggested fix: merge #3 before #4 (or rebase #4 onto #3), and say so in
the PR description. Alternatively, move these README hunks into #3.

### D-2 (Medium): O5 parenthetical

The PR adds: "Saturating 64-bit count (exact up to 63 perfect extensions;
from 64 on it saturates and is not the true count)". The count is
unsigned, and 64 perfect extensions give exactly 2^64 − 1:

- `TestReporter_CountOnlyBinomials` has `{"64 pexs", 64, 1, MaxSize, math.MaxUint64, false}` (wantSat false).
- CLI, two identical n-item transactions, `-s-1`, count-only: n=63 gives `9223372036854775807 set(s)`, n=64 gives `18446744073709551615` (exact), n=65 gives `18446744073709551615` (saturated).

The test's cases are 62/63/64/100 perfect extensions, not "63/64/70".

Suggested Go-behavior text: "Unsigned 64-bit count, exact up to
2^64 − 1 (64 perfect extensions without the empty set); larger counts
saturate at 2^64 − 1 and are then not the true count."

Suggested test text: "`TestReporter_CountOnlyBinomials`: 62/63/64/100
perfect extensions".

### D-5 (Low): AggregateFirst also changes `Value`

`-ts -s2 -el -d0 -v' %e'` on the audit-style r200 data (seed 7) gives 270
sets for each of `-q2`, `-q0` and `-q-2`. But `{a,b,c}` has lift 0.795 /
1.26 / 1.26, and `{b,c,d}` has 0.913 / 0.913 / 1.31. The README sentence
"Without an evaluation threshold, all variants find the same sets with
the same supports" is literally true, but a library user of
`Evaluation` without `Filter` sees different `Value`s per variant.

Suggested addition to README:152 and to P6: "...; the `Value` of a set
under `AggregateFirst` can differ between them too, even without a
threshold."

I checked that `-am`, `-an` and `-aa` give identical sets across 8
variants × 3 targets, with and without `-p0`/`-p-1`/`-p1`.
