# Independent test-methodology and performance audit — fpgrowth-go @ f7bb606

Auditor scope: test suites (root, `internal/*`, `cmd/fpgrowth`, `reference/difftest`,
`reference/bench`), fuzz targets, benchmarks, golden fixtures, `.github/workflows/ci.yml`,
and the claims in README.md, docs/benchmarks.md, docs/m5-investigation.md,
docs/PROGRESS.md, docs/reviews/*.

Clone: `scratchpad/audit/test` at `f7bb606` (verified `git rev-parse`). No existing file
was modified; `git status --porcelain --untracked-files=all` shows nothing outside
`_audit/` after all runs (tests, fuzzing, reference build, difftest, benchmarks).
Throwaway material: `_audit/test/` (logs, regenerated-fixture copy `regen/`, mutants,
probes, comparison outputs `cmp-count/`, `cmp-m5/`).

Machine: Apple M1 Max, 10 cores, macOS (Darwin 25.6.0), go1.27.2 darwin/arm64,
Apple clang (cc). **Other audit agents ran concurrently**: 1-minute load averages
during my runs ranged from 4.5 to 120 (recorded per step below). The project's own
measurements were taken at load 2.6–7.2. Timing differences of tens of percent are
therefore expected noise, not failed reproductions, unless stated otherwise.
Load-insensitive metrics (instruction counts, B/op, pattern counts) are used as the
primary reproduction signal where available.

## Summary verdict

- The correctness test infrastructure is strong and largely as described:
  all suites pass (plain and `-race`, root and `reference/`), coverage 97.0 %,
  all nine fuzz targets ran clean, and **every C-derived golden fixture
  regenerated byte-identically** from the pristine upstream build (one exception:
  a crash exit code, 138 vs 139). Two deliberately injected mutants were caught by
  the C goldens and by difftest.
- Headline performance claims reproduce: Go/C geomean **1.596** (claimed 1.60),
  M5 critic case **19.8 ms / 13.9 MB vs C 224.8 ms / 22.0 MB** (claimed 21 ms /
  14 MiB vs 236 ms / 22 MiB); the "before" figure reproduces only to order of
  magnitude (29.1–29.8 s / 434–496 MiB vs claimed 34.09 s / 673 MiB).
- Weaknesses: stale/contradictory README statements on M5 and tuning measurements
  (TST-1, the only item I would fix before v0.1.0), a degenerate streaming-memory
  test (TST-2), oracle shares the measure functions with the implementation (TST-3),
  inflated "effective" difftest case counts (TST-4), several published numbers
  without a committed harness (TST-5), loose latency assertions (TST-6).

## Findings

### TST-1 — README contradicts the current M5 implementation and the published tuning measurements
- Severity: **Medium**. Status: **confirmed**. Blocks v0.1.0: **yes** (trivial doc fix; the
  README is the release's primary user document and states the opposite of the shipped
  behavior).
- Evidence: `README.md` lines 1018–1023:
  "Closed and maximal item sets with a maximum size (`MaxSize`, CLI `-n`) are searched
  without the depth limit that upstream uses ... A cheaper exact check is scheduled for
  the performance stage." — but docs/m5-investigation.md §1/§8 and PROGRESS say full
  exploration was removed and replaced by a size-limited search with a complete
  extension check (`internal/fpg/extcheck.go`). Lines 1025–1027: "Which settings are
  fastest depends on the data; no measurements are published yet." — docs/benchmarks.md
  publishes Variants tables (`-As -l0`, `-As`, `-Ac -j`, `-Ac`, `-Ad`, `-At`) and
  README line 41 itself links to them.
  Minor: PROGRESS "Sparse data with small `-n` pays up to 1.7× for the check (follow-up:
  incremental covers)" — incremental covers were implemented (benchmarks.md attempt 10);
  my measurement shows Go/C 1.7–3.0 on `sparse-large -n2/-n3`.
- Reproduction: `sed -n 1016,1027p README.md`; compare with `docs/m5-investigation.md` §1.
- Impact: users are told `-n` with closed/maximal may be slow and an improvement is
  pending; the opposite (and a remaining 2–3× cost on large sparse data) is true.
- Resolution: rewrite the paragraph (size-limited search + complete extension check;
  faster than C on dense data, 1.7–3× C on large sparse data); replace "no measurements
  are published yet" with a link to the Variants tables; refresh the PROGRESS line.

### TST-2 — Streaming-memory test exercises a degenerate dataset; heap-only measurement
- Severity: **Medium** (methodology/claim strength). Status: **confirmed**. Blocks: no.
- Evidence: `TestLargeFileStreaming` (source_test.go:715ff) mines at
  `MinSupport: Fraction(0.3)`; the generator (`newGenReader`) puts `i0` in 2/3 and `i1`
  in 1/2 of the lines and 1–6 of 500 other items; only `i0`, `i1` are frequent, so the
  bag has at most 4 distinct transactions. `-v` output:
  `table: file 50.0 MB, 1663779 transactions, heap peak while reading 0.7 MB, while mining 1.3 MB ... 3 sets`.
  The probe samples `runtime.MemStats.HeapAlloc` every 50 000 transactions and once per
  result (not RSS, not stacks, not GC headroom).
  Same-shape 50 MB file through the CLI (`_audit/test/stream50.csv`, awk copy of the
  generator, `/usr/bin/time -l fpgrowth -f, -sX`):
  `-s30`: 3 sets, max RSS 5.96 MB; `-s0.5`: 503 sets, **max RSS 254 MB**; `-s0.05`:
  2003 sets, 255 MB.
- Impact: the test proves that the readers do not retain records; it does not show any
  bound on the bag/tree for realistic data. README does carry the caveat ("that bound
  holds for that data, not in general"), but the sentence still reads as a streaming
  memory claim.
- Resolution: rename/describe it as a "reader does not retain records" test; add a
  second case with a non-trivial bag (e.g. all items frequent) asserting heap is bounded
  by a function of distinct prefixes, not of file size; state "heap (HeapAlloc,
  sampled)" in README.

### TST-3 — Oracle uses the implementation's rule-measure functions
- Severity: **Low** (mitigated). Status: **confirmed by mutation**. Blocks: no.
- Evidence: `internal/oracle` only imports `internal/tract` for the `Supp` type, and its
  mining is an independent bit-mask brute force. But every oracle comparison with an
  evaluation measure takes the function from the implementation:
  `rules_test.go:131`, `fpgrowth_test.go:296/1550`, `internal/istree/report_test.go:33`,
  `internal/fpg/tree_test.go:129` all build
  `oracle.Measure{Func: oracle.MeasureFunc(ruleval.Measure(m).Func()), ...}`. Threshold
  conversions (`oracle/threshold.go`) re-implement C's formulas (by design).
  Mutant (in a copy): `reKulc` factor `0.5` → `0.5000001`
  (`internal/ruleval/measures.go:137`). Result:
  `ok github.com/dimchansky/fpgrowth-go 6.179s` (root package, incl. all oracle
  comparisons and FuzzMineItemsets/FuzzMineRules seeds) — **not detected**;
  `internal/fpg` fails only in `TestTreeGolden` (C golden), `internal/istree`
  (report_golden) and `internal/ruleval` (C fixtures) fail; difftest: 5 FAIL / 2000 small
  cases, 1 / 100 large.
- Impact: the oracle cannot detect measure-formula bugs; detection relies entirely on
  C-derived fixtures and difftest. Docs ("Nothing here reuses the port's mining code")
  are literally true but the "independent oracle" claim does not extend to measures.
- Resolution: state the limitation in `internal/oracle/doc.go` and README "Testing";
  optionally give the oracle independent textbook implementations of a handful of
  measures (confidence, lift, conviction, Kulczynski, chi²) to cross-check `ruleval`.
- Status note (2026-10-19, issue #15): resolved. `internal/oracle` has an independent
  reference for all 25 rule measures and `-eb` (`RefMeasures`, `LogRatioValue`), and
  the oracle comparisons in the root package, `internal/istree` and `internal/fpg`
  use it next to the implementation's functions. The `reKulc` mutant above and
  mutants in chi², information and FisherSupport fail those tests with the C goldens
  skipped (commands and output in the pull request for #15).

### TST-4 — Difftest case counts overstate the effective comparisons
- Severity: **Low**. Status: **confirmed**. Blocks: no.
- Evidence (`_audit/test/difftest-summary.txt`, seed 1): 10 000 cases →
  byte-equal 7 407, semantic 313, tolerated 162, error-equal **1 421** (all
  "fpgrowth: no (frequent) items found"), deviation-verified 697;
  "passed cases with at least one set/rule written: **5 274**"; "Go checked against the
  brute force: 6 021 exactly, **2 558 as a subset** (evaluation measures)"; 36 records
  accepted on one side only at the threshold. Mutation sensitivity: the Kulczynski
  mutant failed 5 of 2 000 cases (0.25 %); an `-S` rounding mutant (`Floor`→`Ceil` in
  `internal/fpg/thresh.go:77`) 18 of 2 000 (0.9 %) — both caught at the default 10 000.
  Target × variant matrix is balanced (≈450 cases per `-t{s,c,m,g,r} × -A{c,d,s,t}`,
  ≈200 for the default).
- Impact: "0 failures in 30 000+ cases" counts ~47 % of cases with no mined output.
  Detection power for option-specific defects is in the per-mille range per case.
- Resolution: report effective numbers (cases with output, exact BF checks) alongside
  totals; bias the generator away from "no frequent items" (e.g. resample when no item
  reaches the threshold); add per-measure sweeps.

### TST-5 — Published numbers without a committed harness
- Severity: **Low**. Status: **confirmed** (absence). Blocks: no.
- Evidence: `grep` finds the README high-cardinality table values (3,812,253;
  14,337,115; 183 MB; Zipf(1.1)) and the 4M-transaction cancellation figures (0.35 s)
  only in README.md / docs/algorithm.md; no generator, test or script. m5 §7 admits the
  `s20000x500` rows are not reproducible and that the dNxKdP rows were measured before
  pinning. My throwaway probe (`_audit/test/cancelprobe/main.go`, 4M × 20 uniform of
  1000, `Fraction(0.01)`): cancel at 0.3/1.5/3/5/8/12 s → latency 54 µs, 0.81 ms,
  1.24 ms, 0.11 ms, 1.05 ms, 104 ms — consistent with the claim; process max RSS
  12.7 GB.
- Impact: these claims cannot be re-validated by a reviewer (AGENTS.md: "never claim ...
  numbers without a command whose output shows it").
- Resolution: commit the probes (e.g. `reference/bench/probes/` or `-run`-gated tests
  behind an env var) or label the numbers "one-off measurement, not reproducible".

### TST-6 — Cancellation latency assertions are 2–3 orders looser than the documented figures
- Severity: **Low**. Status: **confirmed**. Blocks: no.
- Evidence: `cancelLatencyLimit = 500 * time.Millisecond` (fpgrowth_test.go:700),
  `treeBuildLatencyLimit = 50 ms`; README cites "within 2 ms". Observed (load 11):
  Bursts ≤ 33 µs, Fisher 0.17–3.72 ms, TopDownLevel 8.8 ms, TreeBuild ≤ 46 µs.
- Impact: a 100× latency regression in the check placement passes CI. Loose limits are
  reasonable for shared CI runners, but the documented number is untested.
- Resolution: keep the CI limit, but log/collect the latencies (or a tighter limit under
  an env var for local runs); phrase the README as "measured, not asserted".

### TST-7 — Fixture provenance: one non-deterministic C fixture; Go snapshots described as C goldens
- Severity: **Low/Info**. Status: **confirmed**. Blocks: no.
- Evidence: all generators are committed (`reference/harness/*/gen.sh`, `tract/run.sh`).
  Regenerating everything in a copy (`_audit/test/regen`) with the freshly built release
  binary: `git status` shows only
  `cmd/fpgrowth/testdata/golden/dev-bigw.exit: -138 +139` (C crashes with SIGBUS vs
  SIGSEGV; case is deviation M7, Go is checked against `golden-go/`, so the C exit is not
  compared — harmless). fpg (3 143 + 348 cases), ruleval (2 461 tuples), tabread, cconv,
  isrout (33), report (117 scripts), istree (48, incl. the patched build), tract
  (26 sets, 506 cases), CLI (456 files) all byte-identical. `cmd/fpgrowth/testdata/golden-go/`
  holds 105 Go-generated files for 35 deviation cases (rewritten by `-update`); README
  "Testing" says the golden files are "produced by the C reference".
  Goldens were produced on macOS/arm64/clang only; CI's Linux/gcc reference job runs
  difftest but never regenerates the goldens.
- Resolution: normalize crash exit codes to "signal" in the CLI harness; mention
  `golden-go/` as reviewed Go snapshots in README; optionally add a CI step that
  regenerates the goldens on Linux and diffs.

### TST-8 — Coverage gaps in CI's execution matrix (minor)
- Severity: **Info**. Status: **confirmed**. Blocks: no.
- Evidence: benchmarks never execute in CI (compiled by `go vet` only); I ran
  `go test -run '^$' -bench . -benchtime 1x ./...` → all 11 packages ok (34.6 s). The
  reference `-race` job instruments only the harness; the Go CLI under test is built
  with plain `go build`. Under `-race` the randomized suites run 1/5 of the cases.
  difftest reuses an existing `reference/build/release` binary without a staleness
  check (`DIFFTEST_REBUILD` forces a rebuild) — local-only risk, CI is fresh.
  Root tests have no dependency on network, home directory or a C compiler;
  `TestExampleCopies` skips (by design) when `reference/` is absent (module download).
- Resolution: add a `-bench . -benchtime 1x` smoke step to CI.

### PERF-1 — Go/C geomean reproduced
- Severity: **Info**. Status: **confirmed**. Blocks: no.
- Evidence (`_audit/test/cmp-count/summary.md`, `raw.tsv`, load 13.45 → 16.92, 5 runs
  after 1 warmup, interleaved): geomean of median ratios **1.596** over 32 configs
  (claimed 1.60); geomean of per-config minimum walls **1.601**, range **1.11–2.07**
  (claimed 1.12–2.08). Instructions geomean 2.70 (claimed per-row range 2.1–3.9; ours
  2.08–3.93). Per-family geomeans: long 1.10, dense 1.54, sparse 1.83, weighted 1.90,
  large 1.96; family-weighted geomean 1.63 (the config mix, 18 of 32 dense, shifts the
  headline by only ~0.03). Row noise under load is large: `weighted-s` median 2.62
  (Go 56–498 ms, C 28–354 ms), `dense-c-Ad` C 192–625 ms.
- Interpretation: headline reproduced; individual rows at this load are not reliable
  (as the doc itself warns).

### PERF-2 — Go-vs-C methodology gaps
- Severity: **Low**. Status: **confirmed**. Blocks: no.
- Evidence: the geomean is not computed by any committed tool (`grep -i geomean` in
  `reference/` finds nothing; `compare/main.go` only prints medians); `compare.sh`
  records `uptime` once at the start of a whole run; no significance test or CI for the
  Go/C ratios (n = 5, medians and min–max only); the 32-config headline excludes the 15
  M5 rows, where Go is both far faster (0.03–0.09× on dense `-n`) and far slower
  (**1.71–2.99×** on `large-[cm]-n[23]` in my run; doc 2.2–3.2×). README mentions only
  the dense wins.
- Resolution: compute geomeans (count/devnull/file) and per-family geomeans in
  `bench/compare`; log `uptime` per configuration; add the large-sparse `-n` worst case
  to the README sentence.

### PERF-3 — M5 "before" figure inconsistent and only approximately reproducible
- Severity: **Low**. Status: **confirmed**. Blocks: no.
- Evidence: m5-investigation.md §1: "Go 31.6 s / 422 MB"; §7 and PROGRESS:
  "34.09 s / 673 MiB". Rebuilt CLI from `c16c2f5` (`git archive`), pinned
  `d2000x40d60.tab`, `-tc -s2 -n2`, `/dev/null`: 29.77 s / 463.9 MB, 29.10 s / 519.8 MB,
  29.47 s / 454.6 MB (load 8.6 → 6.1). After: 19.8 ms / 13.9 MB; C 224.8 ms / 22.0 MB.
- Impact: none on the conclusion (~1 500× speed-up, ~33× less memory); the peak-memory
  "before" figure varies 422–673 MiB across documents and runs.
- Resolution: quote one measured range with its command, or "≈30 s / 0.4–0.7 GB".

### PERF-4 — In-process Go benchmarks: times higher under load, B/op identical
- Severity: **Info**. Status: **noise / hardware load, not a failed reproduction**.
  Blocks: no.
- Evidence (`_audit/test/gobench.txt`, 6 runs interleaved across the 5 patterns,
  benchstat; load 10.2 → 11.2): Targets/sparse/s=0.1/frequent 35.7 ms ± 5 % (doc final
  28.4), dense/s=5/frequent 496 ms ± 7 % (421), dense/s=5/closed 683 ms ± 2 % (587),
  long/s=3/frequent 240 ms ± 5 % (165), MaxSize/dense/s=2/closed/n=3 595 ms ± 6 % (575),
  Rules/dense/s=10/c=90/n=4 218 ms ± 3 % (173). alloc/op 17.3 / 42.3 / 47.7 / 89.9 /
  46.1 / 33.4 MB — equal to the doc. allocs/op 232–393 (doc: 200–400 range).
- Interpretation: +3 % to +45 % at 2–4× the doc's load is consistent with contention;
  the `long/s=3` +45 % is the largest and should be re-measured on an idle machine
  before anyone relies on the "−24.5 %" optimization delta for that row.

### PERF-5 — Benchmark datasets are synthetic only
- Severity: **Info**. Status: confirmed. Blocks: no.
- Evidence: all datasets come from `reference/bench/gen` (pinned SHA-256; `go test
  ./bench/...` passed). No standard FIMI datasets (retail, kosarak, chess, mushroom,
  accidents) are used; README already says "Validate on your own workloads".
- Resolution: optionally add 2–3 public FIMI datasets (downloaded by the script, not
  committed) to `configs.txt`.

## Positive observations (verified)

- Oracle mining is genuinely independent (bit-mask lattice + superset-sum transform;
  only `tract.Supp` imported); fuzz targets FuzzMine/FuzzMineItemsets/FuzzMineRules
  compare against it.
- difftest compares byte-for-byte first, then semantically with explicit tolerances, and
  every deviation case must pass an independent brute force; when C passes the brute
  force in a flagged case, full equality is required (2 612 such cases in seed 1).
- CI checks that tests leave the checkout unchanged and runs on four OS/arch
  combinations with two Go versions, linux/386, fuzz smoke (9 targets × 20 s), and the
  C reference on Linux/gcc and macOS/clang.
- The bench runner verifies pattern counts across programs, runs and modes (M5 rows:
  Go ≤ C), and interleaves C and Go.
