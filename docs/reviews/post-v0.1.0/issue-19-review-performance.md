## Regressions

### F1 (HIGH, confirmed): the B/2 ski-rental trigger costs up to +34 % wall time on an ordinary data shape

**Construction.** Independent two-tier data (`pr33p/advgen`, `tier.go`):

- R rare items with probability pr and C common items with probability pc.
- smin = 0.9·N·pr²·pc.
- `-tm -n3`.

Each rare pair {u, v} is a parent. Its children are the C common items, and every child is maximal: its cover counts in full. The children's actual work reaches B/2 just before the last child. So the rows are built (B ≈ Σ|t| over cover(P) plus the clearing) and then answer one child, or two.

`sibStats` shows exactly that: `builds:18221 checks:18221`, one row-answered check per build. The miner (the 16-items machine, `csCondSupp`) is about 40 % of the run, and it dilutes the effect.

CLI, n = 5, interleaved; regenerate with `advgen -N 200000 -tR 200 -tC <C> -tpr <pr> -tpc <pc>`:

- Loads were 3.1–6.9. RSS is equal: 283/283 MB and 556/556 MB.
- The in-process sweep (`sweep2.out`; `sibOff` vs `sibAuto` in one binary) agrees: 1.21–1.34 for C = m+1, where m is the number of children that brings the work to B/2. C = 3 at pc ≥ 0.17 builds nothing, so it is equal.
- pprof of w1 with rows: `sibBuild` takes 2.3 s of 10.2 s. `scanMaximal` falls only by the one child that the rows answer.

**Why this matters.**

- The documented "≤ 3.25× per level" is in work units. It is a bound, not a guarantee of non-regression. Here it means about 1.8× on the check share of the run and +34 % overall.
- The proof assumes nothing about how many children follow the build. The adversary only needs C = m+1.
- Building at the **first** child (`sibForce`) is cheaper on w1 (8.62 s, +16 %) than the production rule (9.98 s, +34 %). The pre-build ordinary checks are pure waste whenever the build happens anyway.
- With threshold B instead of B/2 (my experiment, `dbg/`): w1 and w3 build nothing and are equal. But C = 7 (`w4`, pc .20) then shows +6 % in process, against +19 % with B/2. A tighter threshold only moves the adversary.
- The docs claim that no measured configuration got slower (`docs/m5-investigation.md` §7.2 and §8 update, `docs/benchmarks.md`). That holds only for the measured set.

**Fixes requested (one of):**

1. **Use the miner's sibling count.** When the miner reports the children of P, it knows how many frequent items P's conditional database holds, i.e. the number of children. Pass that remaining-children count, or the conditional item count, to `checkPath`. Build only if the remaining children's expected saving exceeds B. For example, build iff remaining × (est_child − rowcost) ≥ B, with est_child taken from the actual work of the children checked so far. This removes the "build for the last child" waste and keeps the target gain: the target has about 67 children per parent.
2. If (1) is too invasive, the orchestrator could accept a bounded regression. That needs the maintainer's explicit sign-off and a documented worst case: add a w1-like `configs.txt` row and state the +30 % in `docs/differences.md` / `m5-investigation.md` §4.1. That contradicts the stated acceptance condition, so it is not my recommendation.

Either way, add the two-tier row (`-tm -n3`, C = m+1) as a no-regression benchmark next to the F1 row.

## Architecture and readability (extsib.go, hooks)

The structure is good:

- One cache per path level, invalidated by `sibReset(k)` in `checkPath`, which is the same rule as the path cache.
- The scratch reset covers every touched item.
- Gates use the actual work.
- The build is a single pass.
- The comments are dense but accurate, with these exceptions:

1. **LOW: comment and docs inaccuracy.**
   - Where: `sibWorth` and `m5-investigation.md` §4.1.
   - Claim: computing the cost only once the work reaches 4·(L+1)·n "delays no build by more than a factor of 2 in work".
   - Problem: the build threshold is B/2 ≥ (L+1)·n/2, so the gate can delay a build by up to 8× B/2 when transactions are short (B ≈ (L+1)·n). I saw this on short-transaction data: no build although the children's work exceeded B/2.
   - Impact: lost gain only, not a regression. Fix the statement, e.g. "at most max(B/2, 4·(L+1)·n)".
2. **LOW: duplicated cost model.** `sibCheck` recomputes `decide`'s estimate inline. Extract `func (c *extChecker) estimate(n int) int64` and use it in both places, so that a future recalibration of `decide` (option B) cannot silently diverge from the sibling gate.
3. **LOW: unit mismatch in the bound.** The 2.25×/3.25× bound counts a build visit and a scan visit as equal. A build visit does `freq` + `slot` + row OR + `supp` add, with random access to `rows`. A scan visit does `inSet` + `cnt`. The F1 profile shows the build is the dominant extra cost. Either calibrate one factor or state that the bound is in visit units, not time.
4. **Info.** `c.work` is incremented once per transaction in the `scanMaximal` hot loop for every maximal check, also when no level can use it (`|prefix| = 1`). No measurable cost: `CloMaxLimited tm` is `~`. `testHooks.checker` is a test-only field in production code, which is acceptable as is.

## R2-1 (HIGH, confirmed): later siblings that are never checked still count in `miner.left` and `freqBelow`, so rows get built for one child

**Mechanism.** Under a size limit, the maximal reporter checks a set only if no frequent superset was found in its subtree. A child P ∪ {h} whose subtree has a frequent set within `zmax` is skipped. Both bounds still count such a child:

- `miner.left` counts the loop entries left;
- `freqBelow[h]` counts the frequent items with a lower code.

So condition 2 sees many children still to come. The rows are built, and then no later check uses them.

**Construction** (`advgen -N 200000 -sR 400 -spr 0.15 -sa 0.8 -sS 4 -sK 10 -sq 0.65 -sall`, `-tm -s-5400 -n3`):

- 400 rare items at 15 % (the parents {u}, level L = 0).
- One of 4 mutually exclusive "slice" items in 80 % of the transactions (like a categorical attribute). {u, s} are maximal children that count their whole cover.
- 10 "spreader" items at 65 % in all transactions. They spread the covers, so the scan path is used, and they are more frequent than the slices, so they come later in the loop. {u, sp, sp′} is frequent, so the children {u, sp} are pruned and never checked.
- After 3 slices the work is ≥ B/2. At the 4th slice, rem = 10, so the build happens. The rows then answer exactly that one child.
- `sibStats`: `builds:399 checks:399`.
- pprof: `sibBuild` is about 9 % of the run, against `scanMaximal` at 14 %.

**CLI, two independent campaigns:**

| --- | ---: | --- | ---: | --- | ---: | --- | --- |

RSS is equal (1239 MB both). Set counts are equal and every exit code is 0.

I did not get a measurable loss from the other suggested directions:

- **"Later children stop much earlier."** After the build, rows also stop early: one popcount of ⌈|cover|/64⌉ words. A non-maximal child's ordinary scan needs at least smin transactions, and a maximal child covers at least smin. So avg overestimates a later child's cost by at most about cover/smin, and the rows still save on most such children. My split-region attempts gave no regression.
- **The 16-items machine's `left` = n or 16.** It overestimates, but `freqBelow` caps rem.
- **Top-down.** w1 `-At` is equal.

**Fix (requested, either):**

1. **Use the bound only where it is exact.** At the level whose children have size `zmax` (depth + 1 = zmax), no child has a subtree, so every later sibling is checked (maximal targets have no same-size subsumption). There `miner.left` and `freqBelow` are tight. At shallower levels, use rem = 0, i.e. require that the current child alone pays, or no build. Re-measure the target and `-n4`: at `-n4` the gain comes from levels below `zmax`.
2. Or have the miner pass the count of later siblings that cannot be pruned. The miner can count the later conditional items whose own conditional database is empty at the size limit.
3. Or obtain the maintainer's explicit acceptance of a bounded regression: add the s400 shape as a `configs.txt` row, and replace "no measured configuration is significantly slower than `main`" (M5 §7.3/§8, `benchmarks.md`) with the measured +7 to +13 %.

## The change, as reviewed

- At the level whose children have the maximum size (L + 2 = zmax), r = min(`freqBelow[h]`, `miner.left`) is used as is.
- At shallower levels, r is scaled by histLater / histBound:
  - Both are sums per level over the completed parents and are never reset.
  - histLater is Σ k(k−1)/2, the later children actually checked.
  - histBound is Σ r, the bounds passed on every check.
  - The scaled value is 0 until the first parent completes.
- Both sums are updated in `sibReset`, so they count exactly the parents that `checkPath` has left.
- It is a cost heuristic only and cannot change a verdict.
- The code is small and clear.

## New adversaries against the history estimator

**Warm-up: early parents that mislead the history.** Rarer "warm-up" parent items w (`-sW`, `-swp`) complete first at the same level L = 0. All their children are checked, so they push histLater/histBound toward 1 before the s400-style parents are processed.

In process (`sibOff` vs `sibAuto` in the same binary):

| data | result |
| --- | --- |
| R 400, K 10, no warm-up | 0.992, 0 builds |
| + W = 100 w at 5 % | **0.888** (faster): 99 builds, 891 row checks, all at the w parents, where they pay off |
| K 20, W = 160 | **0.604** (faster) |

The u parents still did not build. Two couplings defeat this adversary:

- To move the ratio, the warm-up parents need many checked children. Those children are themselves expensive maximal checks, so their own builds pay off.
- Every warm-up item raises nFreq. That raises the row cost per child and closes the gain margin of the misled parents, which is thin: on s400, gain was 2.35 M against B = 2.20 M at rem 10.

**A pure partner-pool warm-up** (`-cV`/`-cK`; the partners are more frequent than v) is ruled out on paper:

- The partner pairs either become frequent and dominate (6× faster in process with rows), or they need about 2.75·k extra frequent items. That kills the row gate at the misled level.

**Mixed levels and alternation.** The history is kept per level index. A run of one kind of parents followed by the other is the same as the warm-up case above. Parents with nothing checked only lower the ratio, which makes builds less likely.

I found no input on which the PR is slower than main.
