# Configurations of the Go-vs-C comparison (reference/bench/compare.sh).
# Format: <id> <input file> <fpgrowth options...>
# Inputs are written by `go run ./bench/gen -all -dir <data>`; thresholds
# are chosen so that every run reports 10^4 to 10^6 patterns (except the
# M5 rows). A trailing "*" on the id marks a size-limited closed/maximal
# configuration where C may report more sets than Go (deviation M5, bug
# B5); its counts are checked per program (Go's never above C's).

# Dense maximal sets of exactly the maximum size (independent audit
# M5A-1, issue #19): every 3-set of d20000x200d30 is frequent at -s2 and
# no 4-set is, so -tm -n3 reports all C(200,3) = 1,313,400 3-sets, each
# after a check that counts its whole cover. Slow (Go about 100 s, C
# about 40 s per -n3 run); select the other M5 rows with an id filter,
# e.g. '^(m5-d[125]000-|m5-tier-|m5-split-|large-[cm]-n)'.
m5-d20000-c-n2*    d20000x200d30.tab -tc -s2 -n2
m5-d20000-m-n2*    d20000x200d30.tab -tm -s2 -n2
m5-d20000-c-n3*    d20000x200d30.tab -tc -s2 -n3
m5-d20000-m-n3*    d20000x200d30.tab -tm -s2 -n3
m5-d20000-m-n3-As* d20000x200d30.tab -tm -s2 -n3 -As
m5-d20000-m-n3-At* d20000x200d30.tab -tm -s2 -n3 -At
m5-d20000-m-n4*    d20000x200d30.tab -tm -s1 -n4
# smin 2 transactions: every check stops at its first frequent extension,
# so sibling rows (issue #19) must not be built (design review F1)
m5-d20000-m-n2-s2* d20000x200d30.tab -tm -s-2 -n2
# Two-tier data (issue #19, performance review F1): each pair of rare
# items is a parent with 4 maximal children; rows built for them would
# pay off for at most one child, so they must not be built (no
# regression against main).
m5-tier-m-n3*      t100000x204c4.tab -tm -s-180 -n3
m5-tier-m-n3-As*   t100000x204c4.tab -tm -s-180 -n3 -As
m5-tier-m-n3-At*   t100000x204c4.tab -tm -s-180 -n3 -At
m5-tier-c-n3*      t100000x204c4.tab -tc -s-180 -n3
# Slices and spreaders (issue #19, performance review R2-1): most
# children of a rare item are never checked (they have frequent
# supersets), so the later-children bound must not be trusted blindly.
m5-split-m-n3*     s50000x414.tab    -tm -s-1350 -n3
m5-split-m-n3-As*  s50000x414.tab    -tm -s-1350 -n3 -As
m5-split-m-n3-At*  s50000x414.tab    -tm -s-1350 -n3 -At

# every item's cover is one long line and short ones, so each closed

lp-c20000-m*       lpc20000.tab      -As -tm -s-2 -n1
# The probe trap (issue #20, challenge H1): the first cover transaction
# of {a_i} holds a covering item among its 4 probes, the shortest one
# does not, so the first one must still be probed.
adv5-20000-c-At*   adv5-20000.tab    -At -q0 -tc -s-2 -n1
adv5-40000-c-At*   adv5-40000.tab    -At -q0 -tc -s-2 -n1
# Slow before issue #20 (and in C): lp100000 for the scaling (Go 27 s
# before the fix, C 14 s), and lpc20000 without item sorting (-q0; -q-1
# and -q-2 alike), where long suffix chains come first in the cover
# words, so that neither the first transaction nor the spread probes are
# short (Go 58 s before the fix; the C program grew to a 169 GB memory
# footprint and was killed after 541 s, so compare.sh cannot complete
# this row).
lp-100000-c-As*    lp100000.tab      -As -tc -s-2 -n1
lp-c20000-c-q0*    lpc20000.tab      -As -tc -s-2 -n1 -q0
# The perfect-extension chain (issue #21, NEW-1, T4 of the performance
# audit): every item of the chain has all its predecessors as perfect
# extensions, which a maximum size of 1 makes useless; collecting,
# expanding and removing them is quadratic in Go and C. (At 100,000
# items C needs a raised stack limit, M10; these sizes do not.)
t4-6250-s          t4-6250.tab       -s-17 -n1
